# Master Alchemy Taxonomy
## C2O / UNIVERSALIS — Operating Systems and Applications

**Document status:** Foundational taxonomy baseline — v0.1.0  
**Scope:** Exactly four repositories: C2O-OS, C2O-App, UNIVERSALIS-OS, UNIVERSALIS-App.  
**Classification:** Proposed ontology and capability taxonomy; not a claim that every listed capability is scientifically realizable or already implemented.

---

## 1. Purpose and governing model

This taxonomy identifies Alchemies that the C2O / UNIVERSALIS ecosystem must support, understand, develop, govern, verify, or prevent. Every listed item is an Alchemy or a named Alchemy specialization—not an ordinary software feature category.

The taxonomy has two complementary orientations:

- **Support Alchemies:** cultivate beneficial, constructive, truthful, safe, ethical and greater-good outcomes.
- **Protective / prevention Alchemies:** identify, resist, contain, mitigate and recover from harmful, destructive, deceptive, coercive, exploitative or unauthorized outcomes.

A harmful capability may be classified so that it can be understood and defended against. Classification does not authorize its implementation or use. Safeguards must preserve human dignity, autonomy, consent, privacy, legitimate freedom, and lawful activity.

## 2. Four-repository system structure

| Repository | Edition | System responsibility |
|---|---|---|
| C2O-OS | Company / private-source | Shared OS architecture with private-source governance, proprietary implementation and company-controlled authority |
| C2O-App | Company / private-source | Shared application architecture with private-source governance and company-controlled distribution |
| UNIVERSALIS-OS | Public / open-source | Same underlying OS capability architecture, independently inspectable and operable under open-source governance |
| UNIVERSALIS-App | Public / open-source | Same underlying application capability architecture, independently inspectable and operable under open-source governance |

C2O-OS and UNIVERSALIS-OS are the same underlying OS system expressed as different governance and distribution editions. C2O-App and UNIVERSALIS-App are likewise the same underlying application system expressed as different editions. The four repositories are not four unrelated capability ontologies.

Shared taxonomy definitions and public contracts must not expose C2O private keys, proprietary policies, confidential incident data, or private implementation details. UNIVERSALIS must remain independently operable and must not acquire permanent dependency on C2O authority.

## 3. Intelligence ontology and boundaries

Only the following intelligence entities are included:

1. **C2O** — private-source company intelligence.
2. **UNIVERSALIS** — public/open-source intelligence.
3. **UNIVERSALIN / UNIVERSALINS** — non-personal assistant designation(s). UNIVERSALINS support humans, the technological grid, both OSs, both Apps, and the wider world.
4. **UNIVERSALIN Guardian / UNIVERSALIN Guardians** — personal human AI Guardian designation(s), supporting individual humans and, where authorized, their OS, Apps, activities and robotics.

UNIVERSALINS and Guardians are distinct assistant classes. UNIVERSALINS provide non-personal, domain or system assistance; Guardians provide personal assistance under the individual's authorization. Neither class is an independent owner or authority over a human or system. No other intelligence entities are introduced by this taxonomy.

## A. Source interpretation

## F. Measurement and verification model

Every implementation claim must distinguish at least these measures:

- **Activation latency:** request accepted to authorized operation start.
- **Preparation latency:** start of preparation to readiness.
- **Charging/resource-acquisition time:** time to reach a defined resource-ready threshold.
- **Control latency:** input or command to effective control response.
- **Execution duration:** operation start to operation completion.
- **Transition latency:** valid state-change request to stable target state.
- **End-to-end latency:** request to verified completion.
- **Throughput:** valid completed operations per unit time.
- **Precision/correctness:** conformance to expected output and control tolerances.
- **Resource cost:** compute, memory, energy, bandwidth, thermal load, and other relevant resource consumption.
- **Failure and retry rate:** unsuccessful operations and retries under comparable conditions.

Verification must use a documented baseline, representative workload, repeated measurements, defined percentile reporting where appropriate, and comparable hardware/software conditions. Faster is not automatically better: an optimization that increases errors, unsafe actions, resource exhaustion, unfairness, or policy bypass fails acceptance.

## G. Verification requirements

Any implementation claiming support for Adaptive-Attacks Alchemy must demonstrate, as applicable:

- A clearly defined target domain and legitimate purpose; no unapproved real-world target.
- Explicit separation between fictional/simulated actions and real-world operations.
- A documented baseline action and the exact conditions that trigger adaptation.
- Provenance and integrity checks for every input used to adapt an action.
- Explicit maximum output, scope, rate, resource, and duration limits.
- Authorization and policy checks before every real-world operation or consequential state change.
- Validation that the adapted action still satisfies the intended objective and safety constraints.
- Detection of oscillation, runaway escalation, feedback poisoning, and unstable adaptation.
- A tested stop, rollback, or safe-degradation path.
- Audit records showing the initial state, trigger, inputs, transformation, policy decision, resulting action, and outcome.
- Tests for adversarial inputs, invalid feedback, unavailable information, conflicting constraints, and adaptation failure.
- Evidence that defensive controls cannot be silently bypassed by the adaptation mechanism.

A system that merely changes an attack's appearance in a fictional simulation must not claim real-world adaptive combat capability. A system that adapts defensive testing or simulated adversarial scenarios must document its authorized scope and safeguards.
